## Description
Replace the blind FTS5 pre-search (user message → searchCtx) with Anthropic tool use.
Claude gets a `search_vault` tool it can call with proper filters, sorting, and limits.
The bridge runs an agentic loop (up to 5 API calls per user message) until Claude has enough data to produce a final response.

## Root Cause of Original Bug
- `SendChatMessage` ran `Store.Search(content, PageSize=10)` using the raw user message as FTS5 query
- Natural language like "show me the last 10 items" has no keyword matches → returns nothing
- Even when results existed, no sort-by-time option → wrong items returned
- Claude correctly reported "no search results provided" because there were none

## Acceptance Criteria
- [x] Claude can call `search_vault` tool with: query, type, statuses, priorities, projects, contexts, tags, sort_by, sort_dir, limit
- [x] Tool execution hits the real vault store
- [x] Agentic loop: max 5 iterations, handles `end_turn` and `tool_use` stop reasons
- [x] "Show me last 10 items" → Claude uses sort_by=created_at, sort_dir=desc, limit=10
- [x] Mutations still use JSON code fence → ActionProposal flow unchanged
- [x] `go build .` clean; `npx tsc --noEmit` clean

## Files Changed
- `chat/models.go` — added `BridgeStore` interface (`Search`, `GetItem`)
- `chat/bridge.go` — major rewrite: tool definitions, agentic loop, `callAPI()`, `executeTool()`, `executeSearchVault()`, `extractTextFromContent()`, updated system prompt
- `app.go` — removed blind pre-search block; pass `activeStore` as `chat.BridgeStore` to `BridgeRequest.Store`; removed unused `encoding/json` import

## Key Decisions
- Tool type default: empty → "all" (both todos and notes), overriding store's backward-compat default of "todo"
- Notes truncated to 400 chars in tool results to keep token count manageable
- Max 5 tool iterations prevents infinite loops
- API errors returned as ChatResponse.Error (displayed in UI) not Go errors
- Mutations unchanged: JSON code fence → extractAction() → ActionProposal flow
